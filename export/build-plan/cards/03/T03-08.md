## Goal
The stateful core under the ledger API: the runtime object that owns 03's tables on behalf of whoever calls the ledger (other modules post and hold through it, so their writes to 03 tables go through a store handle bound to module '03'), the entity registry with `registerEntity` exactly as GLOBAL-CONTEXT G7 names it, lazily opened accounts, the full `HoldApi` (place, reduce, release, expiry), the facts table through which later modules push the inputs 03 needs (event edges), the per-tick entry queue, and the `RailState` implementation the templates use. It also implements invariant INV-BS-011 (holds never exceed the balance; every expired hold released; no quantity pledged twice).

## Implementation steps
1. `runtime.ts`: `LedgerRuntime` is **built and owned by the ledger**, never by a caller's context. `LedgerWorld.runtime()` (on the flat tree, `world.ts`) hands back the handle over the world's own state — `own` = the 03 table writer, `read` = committed plus this tick's 03 rows, `tick` = the open tick, `partitionId` = the world's partition, `queue` = the tick's `TickQueue`, `catalog`. T03-09's `LedgerPartitionImpl` builds the same object per (partition, module, phase, tick) with `own` = `store.bind({ module: '03', phase })` and `read` = the partition store, and installs it under the `RUNTIME` symbol on the `LedgerApi` object. **There is no `runtimeOf(ctx)` and no `ctx.fail('INV-LED-009', …)` here**: the ledger takes no `PhaseCtx` (E-80.4), so an absent handle is a type error at the call site, and a function that cannot proceed throws (`ensureAccount` on a malformed key or an unknown chart code) — T03-09's adapter turns the throw into its `ctx.fail` record at the module boundary, where a ctx exists. `INV-LED-009` is the P13 writer check (`committed balances changed outside the ledger writer`), not a missing-runtime code.
2. `registerEntity(spec)` on `LedgerWorld` (GLOBAL G7, 03 §3.1), the world being what T03-09 binds to the partition's store: it takes **only the spec**, no ctx. If an entity with `spec.id` exists, return its id unchanged (idempotent). Otherwise validate (`ENTITY_ID_MAX`, `ENTITY_ID_RE`, `kind = spec.kind ?? kindOfId(id)`) and create `LedgerEntity`: `nameKey` default `entity.<id>`; `homeBloc` = `spec.homeBloc` only — the ledger cannot see content, so the city → bloc lookup stays with the caller (there is no `ctx.content`); `homeCity` copied when given; characters always `reportingCcy 'FDL'`, every other kind `spec.reportingCcy ?? 'FDL'` (03 §2.1); `partitionId` = `spec.partitionId` (absent = `undefined`; the world's own partition is `LedgerWorld.partitionId` and `isRemoteAccount` compares against `rt.partitionId`, not a header); `status 'ACTIVE'`; `createdTick` = the world's open tick; rails `payFrom`/`receiveInto` default `{ kind: 'CASH' }`. The row goes in first, then `rootOwnerId` = `rootOwnerOf` and `perimeter` = `perimeterOf` are computed from it (the walk reads the entity map). No accounts are created (lazy, 03 §3.1.2). The constructor registers the genesis entities `sys_SYSTEM`, `cbk_<ccy>` per currency and the escrow court (T03-28 registers the rest). Ownership/perimeter recomputation on control changes is T03-16.
3. `ensureAccount(rt, key)`: parse the key (malformed → throw); reject an unknown chart code by **throwing** — a missing `chartEntry(code)` is a hard error, reported as `ctx.fail('INV-LED-007', [entityId], 'code=<code>', 'chart code')` by T03-09's adapter at the module boundary (`INV-LED-007` is the P13 posting-shape check, not a capture function in the ledger); class from `classOfCode`; `isMoney = isMoneyCode(code, kindOfId(entityId))`; `assetId = sub` for qty-bearing codes (T03-01 step 2); balance 0n, qty 0n for qty-bearing; `openedTick = rt.tick`; written through `rt.own.put('led.account', row)`.
4. Holds (02 §3.14.3, GLOBAL G7 `HoldApi` exactly, with `HoldApiExt` an alias of it — E-79 point 4): the object is the world's `apiFor(module, phase).holds` and a new hold's id comes from the world's own counter (`hld_<26-digit>`), not from `ctx.newId`:
   - `placeCash(owner, ccy, amt, expiresTick, ref)` = `placeCashFor(owner, ccy, amt, expiresTick, ref, '')` where purpose '' means "restricted cash not allowed" (the safe default: a hold without a purpose never relies on restricted cash).
   - `placeCashFor`: unknown owner → `LED_UNKNOWN_ENTITY` (the code `HOLD_REJECT` does not carry); `LED_BAD_EXPIRY` if `expiresTick < tick`; `LED_ENTITY_FROZEN` if owner status is FROZEN or IN_INSOLVENCY (court freeze and insolvency freeze, 03 §3.14.3), or fact COURT_FREEZE true; `amt <= 0n` → `LED_INSUFFICIENT_FUNDS`; parts = the pay-from account plus the owner's restricted 1001 lots, less frozen sources (a BANK pay-from with BANK_FROZEN is skipped, 03 §8 edge 2) and with the restricted lots only when the purpose is in `RESTRICTED_OK_CODES`; if Σ spendable of the parts < amt → `LED_INSUFFICIENT_FUNDS`, except when the shortfall would be covered by restricted cash that the purpose may not use → `LED_RESTRICTED_FUNDS` (acceptance test 03#32 relies on this code; T03-12 tests it). On success write a Hold `{ holdId, kind 'CASH', ccy, parts, amount, remaining = amount, expiresTick, ref, placedTick = tick, crossPartition, purposeCode, status 'ACTIVE' }` and return its id.
   - `placeQty(owner, assetId, qty, expiresTick, ref)`: the same expiry and freeze checks; accounts of the owner holding `assetId` (index byAsset, sorted by key); first with `committedQty − active qty holds ≥ qty` → one part naming that account (so I12 can compute); else `LED_INSUFFICIENT_QTY`.
   - `reduce(holdId, by)`: `remaining = max(0n, remaining − by)`, parts reduced in reverse draw order, status RELEASED at 0n; `release(holdId)`: status RELEASED; `get` returns a copy; `activeHolds(owner)`: the owner's ACTIVE holds in id order.
   - Holds are never visible to other players (L11): the hold table has no view in 03 except the owner's own (T03-27).
5. `consumeHold` (called by T03-09 when an entry with `holdId` is applied): subtract consumed amounts from the matching parts' `remaining`; the hold stays ACTIVE (a resting order may fill again) until released or expired; `remaining` reaching 0n sets status SETTLED.
6. `expireHolds`: every ACTIVE hold with `expiresTick < tick` → RELEASED (02 §3.14.3 rule 3).
7. Facts: id `${kind}:${subjectId}`, written through `rt.own` with `tick`; documented producers in the `LedgerFactKind` comments (T03-01). Tests seed facts with `putFact` in `asSystem`.
8. `TickQueue`: one per tick per partition, held by the provider (T03-09) in memory; `queuedDebit(key)` is maintained on push: for each posting crediting a money account (a credit reduces an asset balance), add the amount; entries carrying `holdId` add only the part beyond the hold's remaining on that account.
9. Cross-partition legs (03 §3.3.5): the rail state marks an account as remote when its entity's `partitionId !== rt.partitionId`; remote balances are not known locally, so `spendable` of a remote account is never consulted (holds are always local, 02 §3.14.3 rule 1). Splitting into legs is T03-09.
10. `INV_BS_011` (scope TICK, severity FATAL per 20 §3.1's catalogue row — it overrides this card's earlier "QUARANTINE" wording; costClass O_TOUCHED): a pure `Check` = `(v: CheckView) => Failure[]` over the **staged `CheckView`** that P13 builds (not `ledgerView`: see Exports), with `v.holds` the staged hold table (expiry already applied) and `v.post` the staged balances: for every ACTIVE cash hold part, Σ remaining per account ≤ the `v.post` balance of that account (I11; "available balance before the holds"); every ACTIVE hold with `expiresTick < v.tick` fails `I11b`; for every quantity account, Σ remaining of ACTIVE qty holds ≤ the staged qty (I12: a qty pledged at most once; 07 records pledges as qty holds with the loan's maturity as expiry). Observed `I11: account=<key> holds=<n> balance=<b>` etc.
