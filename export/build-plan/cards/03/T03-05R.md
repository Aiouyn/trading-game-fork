## Goal

## Why this is a re-cut, in the code's own words
`packages/engine/ledger/src/invariants.ts:619-621` says, of `ledgerInvariant`:

> *"`ledgerView` (the shared check view) lands with T03-05's re-cut card; until then the wrapper reads the postings and the hold rows from the 20A context directly."*

The named card does not exist; `BUILD-ORDER.md` has no row that owns it. The tree therefore carries a **contract gap, not a bug**: `ledgerInvariant` works, T03-08's check works, and 11 cards' Import lines name at least one of the six symbols that are not exported (of the 25 cards carrying a `- T03-05:` bullet). The three reasons T03-05's block cannot simply be kept:

1. **The block's file layout is forbidden.** It puts the members in `packages/engine/ledger/invariants/types.ts` (T03-05 card, `files:` line 20). E-79 part 1 forbids it: every T03 card builds into the existing **flat** `packages/engine/ledger/src`, `invariants/*` is read as `invariants.ts`, no new subdirectory is created under `packages/engine/ledger/`, and the test goes to `packages/engine/ledger/test/`.
2. **The block reads the catalog through `getCatalog()`** (T03-05 card: `catalog: ReasonCatalog` on line 68 of the block, and `getCatalog` on line 54). E-79 part 3 supersedes it: there is no `getCatalog()`; callers use `LedgerWorld.catalog`.
3. **The block's view cannot replace the workaround it is named for.** The comment at :619-621 says the wrapper reads *"the postings and the hold rows"* from the 20A context, but the block's `LedgerCheckView` lists no hold rows at all. As written, `ledgerView` would land and the wrapper would still have to reach into `ctx.post` for `led.hold`. The hold rows are added to the view here (resolution R2), so the sentence at :619-621 can be deleted when this card lands.

## Resolutions (the block left these open; they are decided here, not left to the implementer)

- **R1 — which view survives. Both do, and neither substitutes for the other.** `CheckView` (`invariants.ts:25`) **survives, unmodified**, as the P13 runtime view that the **24** shipped `Check`s consume (`TICK_INVARIANTS` 17 + `SYS_INVARIANTS` 7); it is **not** retired, because eight of its members have no source in a 20A context at all — `flows` (with `flows.sysSide`), `dayEntries`, `flowsToday`, `dayHistory`, `todayByCode`, `alarm`, `facts`, `sys`. `LedgerCheckView` **survives** as the 20A-context view that `InvariantImpl` checks consume from T03-09/T03-10 on. **Neither is a subtype of the other**, and the card states why so no one casts between them: `pre`/`post` are the raw `TruthStoreRead` on one and the materialised `Accounts` map (`SortedMap<string, Bal>`) on the other, and the member sets differ in both directions (**eight** members no `CheckView` has — `partitionId`, `postings`, `before`, `after`, `touchedAccounts`, `touchedEntities`, `events`, `num` — against the eight runtime-only members listed above). **Five names are shared with identical meaning** — `tick`, `isDayClose`, `catalog`, `entries`, `holds` — while `CheckView.entity(id)` corresponds to `before`/`after` only by analogy (different signature, different lookup), so it is not a shared name. Moving a check from one view to the other is therefore a rewrite of its read sites, never a cast. **The cost of each wrong turn, stated so the implementer does not have to decide it:** retiring `CheckView` means rewriting **24** shipped checks and their 5 test files; widening it to absorb `LedgerCheckView` forces the 20A members on a P13 builder that cannot supply them (`postings`, `num(paramKey)` and the `bump`-free `touchedAccounts` exist only in an `InvariantCtx`). The boundary rule: *a check whose data source is the tick's tables runs on `LedgerCheckView`; a check that reads aggregator output or the sys-side flows runs on `CheckView` inside P13.* `TICK_INVARIANTS` and `SYS_INVARIANTS` are **not** migrated by this card (T03-10 owns the `SubCheck` migration).
- **R2 — the view vends the hold rows.** Added `holds`, because the comment this card exists to retire says the wrapper reads them. `escrows` and `accruals` are **cut**: no 20A-scoped check reads them today (`invariants.ts:40-42` declares them for `INV-LED-022`/`-024`, both `sysinv.ts` `Check`s), and a future card that needs one adds a single member — one `post.iter` each.
- **R3 — `I_CHECK_TO_INV` maps to a list, not a string.** T03-05's block types it `Record<string, string>`, and a `string` value cannot express what the tree already emits: **measured, `I1` is emitted by both `INV-LED-002` and `INV-LED-007`, and `I4` by both `INV-LED-003` and `INV-LED-004`** (20 distinct `(id, I)` pairs over 18 I-numbers at the head; those are the two I-numbers carrying more than one shipped id today). The block's own comment says the same in prose for `I1`, and its tick/day split puts `I5`-`I8` under two ids each, so the list value is also what the block intends. A `string` value would force a rename of shipped `observed` strings; the list value keeps every shipped string untouched.
- **R4 — `touchedAccounts` is a set.** Sorted **and** de-duplicated: a `writeSet` can carry several writes on one account, and `touchedEntities` derives from it, so a duplicate would double an entity in the second list.
- **R5 — the catalog is the second argument.** `ledgerView(ctx, catalog)`: the `ctx` parameter is the workaround's parameter, untyped-differently, because that is the call the wrapper already makes; the catalog cannot come from the ctx and E-79 part 3 forbids a module-level `getCatalog()`, so it is passed in from `LedgerWorld.catalog`.
- **R6 — the memo key is the `ctx` object, not `(tick, partitionId, scope)`.** Two distinct contexts can share that triple (two fixtures in one test, or two modules in one tick), and a memo on that key would serve the first context's rows to the second. A `WeakMap<InvariantCtx<Posting>, LedgerCheckView>` gives "derived once per check, per ctx" with no cross-context aliasing, and it is observable (AC-03-05R-VIEW-MEMO).
- **R7 — `QTY_ONLY_CODES` is declared once, in `catalog.ts`, and imported by the I1 check.** Not a copy: the `const` at `invariants.ts:48` is **deleted** and replaced by the import, so the array the check reads *is* the exported array. This is the same shape and the same file as `ESCROW_ONLY_CODES` (`catalog.ts:36`), which is the house precedent for a rule list. E-81 is not touched: `QTY_ONLY_CODES` adds no catalog row, and its two members stay ordinary `catalog.csv` rows (`LED_DISSOLUTION` owner 03, **`EQ_SPLIT` owner 06**) — do not "fix" that owner, and do not treat this list as a catalog source.
- **R8 — `LEDGER_INV_BASE` becomes the single source of the three def fields.** `ledgerInvariant` currently repeats the three literals; it must spread the constant instead (`{ ...def, scope: 'TICK', ...LEDGER_INV_BASE }`). Its signature does **not** change: `scope` stays `'TICK'`, so `test/erasure.test.ts:30-37` keeps compiling and passing unedited. DAY_CLOSE-scoped invariants are built by T03-10's `composeInvariant(def, subChecks)`, whose `def` carries its own scope; nothing here needs to widen `ledgerInvariant`.
- **R9 — `Check` and `CheckView` are not touched at all.** Not exported, not renamed, not re-typed. `INV_BS_011` stays `Check`; this card only makes it *possible* for a later card to express it as a `SubCheck` (R2 gives it the hold rows), and that later rewrite is three `post` read sites, not this card's work.
