## G4. Time (00 §5.1)

5 real seconds per tick; 720 ticks per game day (= 1 real hour); 30 ticks per game hour; one tick = 2 game minutes. Week = 7 game days (Mon–Fri trading, Sat–Sun weekend). Quarter = 13 weeks = 91 game days, months 28/28/35 days. Year = 364 game days = 262,080 ticks. Chapter = 8 real weeks = 1,344 game days. Real day = 24 game days.
Trading day tick-of-day `t`: pre-market 0–59; opening auction t=60; continuous 61–539; closing auction t=540; after-hours 541–719. Accruals (interest, rent, wages, fees) post at day close t=719. Business operations run once per game hour, staggered: an entity runs when `tickOfDay mod 30 == fnv1a32(id) mod 30`.

## G5. Tick pipeline (00 §5.2)

```
P0 ingest  P1 validate  P2 calendar  P3 world(16)  P4 npc(05,16)  P5 ai(11)  P6 match(05,06)
P7 clear(07)  P8 finance(07,08)  P9 real(09,10)  P10 conflict(12)  P11 law(13)  P12 social(14,15)
P13 ledger(03: commit postings atomically, settle/release holds, assert invariants)  P14 emit
```
A phase may read any committed state and the outputs of earlier phases of this tick; it writes only its own module's tables and queues postings for P13. Postings never commit before P13. A failed invariant rolls the tick back and replays it in safe mode. Consequences of tick N that other modules react to land in tick N+1 (via `ctx.send(..., 'NEXT')` or events).

### G6.1 Ports for later modules (dependency inversion)

A module may never import a module built after it. When its rules need data from a later module (for example 05 needs fundamental values from 09 or index weights from 08), it declares a **port**: a TypeScript interface in its own `ports.ts` (e.g. `MarketPorts`), and its factory takes the implementations: `createMarketsModule(ports: Partial<MarketPorts>)`. The later module exports an implementation of that port, and `packages/engine/index.ts` wires them when building the world. A missing port uses the default the spec gives for "module not present" (stated in the card), never an invented rule.

## G8. Determinism rules (02 §3.7, 19 Rule 3.6.2) — lint-enforced in packages/engine

Forbidden in engine code: `Date`, `performance`, `Math.random`, `crypto` randomness, timers, `process`, `globalThis`, `Intl`, `toLocaleString`, `localeCompare`, `async/await`/Promises, `for…in`, iterating `Object.keys/values/entries` of map-like objects, `Map`/`Set` iteration where order matters (use `SortedMap`/`SortedSet`), `Array.sort` without a total comparator (use `sortBy`), `JSON.stringify` for hashing/persistence (use `canonEncode`), `WeakMap/WeakRef`, `Math.exp/log/pow/sin/cos/tan/atan2/cbrt/hypot/...` (use `dmath`), `Math.round` (use `roundHalfEven`), `Number` for money or quantities. Allowed raw math: `+ - * /`, `Math.sqrt/abs/floor/ceil/trunc/min/max/sign/fround/imul/clz32`.
NaN/Infinity are illegal in state. Ties are broken by entity id then intent id. Iterate collections only in sorted order. Rejection sampling is forbidden; each variate uses a fixed number of draws. A module may draw only from its own streams. Split money into parts only with `allocate`. No exceptions for control flow: report impossible states with `ctx.fail`.

## Goal
Owner direction (relayed by City Dev): every industry sector sits in the city "in a realistic real world way", and the existing map is kept and improved. This card owns the **rules**: for each of the 13 business sectors of 09 §3.1.4, which district roles and lot types it may use and prefers, a plausible footprint, adjacency and nuisance buffers, and hard exclusions. It also owns how parcel, zoning and sector data drive a **deterministic** assignment. Studio owns the **look**. This card only emits style hook ids (`styleKey`, `densityBand`) and specifies no visuals.

Placement is **legibility, not economics** - and this card now says exactly how much of that it can **enforce**, because the earlier claim ("nothing this card emits enters V, rent, `amenityMult`, `location_j`, appraisal or demand") was **withdrawn by Quant on 2026-10-22** as broader than the card can prove, and as **false** for two distinct paths.

**The boundary the card now claims (Quant's own words, the ruling of record).**
> "placement neither reads nor writes V, rent, `amenityMult`, `location_j`, appraisal or demand; it does not determine which use class exists in which district (zoning does); its per-mille numbers are not calibrated to any economic quantity; and the residual channel - which sector sits where changes which jobs sit where - is a genesis-time property, named, bounded and tested."

**What the card enforces (the narrow claim).** The placement code **neither reads nor writes** V, rent, `amenityMult`, `location_j` (10 §3.15.3), appraisal or demand, and the mix's per-mille numbers are **not calibrated** to any of them. The direct half of that is a static import scan in both directions (AC-10A-12-ISOLATION); the indirect half is tested by AC-10A-12-NO-ECON clause 2, which has **three** sub-clauses.

**Both indirect paths, named.** Placement cannot reach the economy by an import, but it can reach it **semantically**. There are **two** paths, and the second one is the larger:

- **Path A - the use-class channel.** placement decides which sector takes a parcel, the sector's **use class** follows from that, and use class drives **jobs** -> `jobsAccess_d` (10 §3.5) -> `D_d` -> rent -> household district choice `U_d` -> district demand -> `location_j` -> 09 `u_j` -> revenue. A static import scan **cannot catch** this chain, so the card bounds it with a test rather than denying it.
- **Path B - the floor-space channel (first-order, not a derivative).** placement -> use class -> **NPC pool `<use>` segment** -> `supply_{d,u}` (10 §3.4.3) -> pressure -> rent / vacancy / price index -> appraisal (`V_inc`) -> NOI. `supply_{d,u}` is the **stock**, so this path moves rents by **percent**, not basis points. It was live because of **IR-2** ("seed the NPC pools' facility mix from it") and the pool key is `<districtId>|<use>|<grade>`.

**Path B is closed by construction by clause 2.3** (AC-10A-12-NO-ECON): a pool's `<use>` comes from the parcel's **zoned use** (T10A-03), never from the placed facility's sector. Placement may shape the composition *within* a use class; it may not decide *which* use classes exist where, and it may never set a pool's stock level.

**Why the residual Path A channel is a tolerated consequence and not a violation** (recorded so the next reader does not re-raise it). The channel is a **genesis-time structural property no player can re-roll** (INV-PLC-3; 10 §3.19.1 - regions already generated keep their assignments); the **economics -> placement** direction is untouched (V and zoning feed placement, and placement runs at stage 7b, after stage 7 land value and zoning); and it is **small and self-limiting**. Quant measured it from the spec's own coefficients, first order: `dD_d = 0.30*d(tanh(2x))`, `dlocation_j = 0.50*dD_d`, 90-day rent = `0.15*dD_d`, 09 `u_j` coefficient `d` = 0.1-0.7 by segment. A **1% job-attribute shift at the mean** moves 90-day rent by **9 basis points** and a business's market share by **0.15%**, and `tanh` saturates it (at 3x the mean, **0.000%**).

Zoning (10 §3.19.4) stays the only thing that permits a use. This card narrows *which sector* takes a permitted parcel and refuses a sector that zoning permits but realism forbids (for example a refinery on an INDUSTRIAL parcel 40 m from housing).

### One signature change from the pre-recut card (and why)
`districtRole(d, terrainRole)` keeps its signature, but the **`role` column of `district-flags.json` is authoritative** and `classify.ts` must produce exactly the shipped values. The derivation order is fixed, and it is the same order T10A-13's own test (`AC-10A-13-RULES-ROLE`) asserts for all 105 rows, which passes on the shipped file:
**cbd -> port -> working -> trophy -> prime -> station (mid) -> riverOrCanal (mid) -> MIXED_CORE.**
Concretely, for a district of tier `t` with flags `{cbd, port, station, riverOrCanal}`:
1. `cbd` -> `CBD`
2. `port` -> `PORT`
3. tier `working` -> `INDUSTRIAL`
4. tier `trophy` -> `TROPHY_RES`
5. tier `prime` -> `PRIME_RES`
6. tier `mid` and `station` -> `TRANSIT_HUB`
7. tier `mid` and `riverOrCanal` -> `MIXED_RIVER`
8. tier `mid` otherwise -> `MIXED_CORE`
The `terrainRole` parameter stays because the terrain role is still the input for the `WATERFRONT` need and the E-78.1 waterfront check (a `port: true` district's terrain role must be `waterfront`, `industrial_shore` or `island`).
The 105-row table gives the AC-10A-12-ROLE-PA fixture for free: the 8 Port Avalon districts map to the 8 roles named in "Sector rules" below.

#### Where the tier comes from (the tier fix, Producer ruling 2026-10-22, round 3)
**The tier input is 22 §3.3's `Tier` column** (`working` | `mid` | `prime` | `trophy`), the same column T10A-13's shipped test reads and the same column the shipped `role` column was derived from. It is **not** a value this card invents, and it is **not** in `packages/content/data/district-flags.json` - **that file carries no tier column** (see Tree check 4), so the derivation needs a second input.

**T10A-02 is not built and this card does not wait for it.** `packages/engine/city/geography.ts` (T10A-02's file) does not exist on `origin/main` (verified: `git ls-tree -r --name-only origin/main -- packages/engine/city/` returns nothing), and T10A-12 creates `packages/citygen/**` itself, so the two packages do not meet here. The tier therefore arrives as **authored content read the same way `district-flags.json` is read**: 22 §3.3 is a spec table, so the tier reaches `classify.ts` as **data, not as an import of T10A-02's module**.

**`classify.ts` must DERIVE the tier, never copy it.** `classify.ts` owns a `DISTRICT_TIER` table (105 rows: `distId` -> tier), and `districtRole` consumes that tier alongside the flags. The value it returns is the tier the shipped `role` column was derived from - not the `role` column, and not a second copy of a derivation.

**Where the tier table lives, and who owns it.** The tier table is **22 §3.3's `Tier` column, verbatim** - the same 105 rows, the same ids, no new names and no new tiers (E-78.1 and E-80 do not touch tier). It is **content**, so it belongs to the content package next to the flags. **It is a separate file, and it has to be**: `district-flags.json` has a **closed field set** (T10A-13's shipped test asserts it, and its 13-mutant baseline kills any row that gains a field), so adding a `tier` column there would break `AC-10A-13-SCHEMA` on a shipped, QA-verified file this card does not own. So the tier goes in a **new** file, `packages/content/data/district-tiers.json`, and City Dev transcribes it.

**The tier table needs no authoring, and the card carries no 105-row copy.** Unlike T10A-13's flags - which were **design decisions** and therefore needed a card-side values table - the tier is **already written down in 22 §3.3**. So this card does not re-list 105 rows it would only duplicate: City Dev transcribes 22 §3.3's `Tier` column, and `packages/content/src/district-tiers.test.ts` reads **22 §3.3 at test time** and asserts the file matches it row for row - the same "read the spec, compare" discipline T10A-13's shipped test uses. The card's role is to **name the source**; the test is what makes the copy honest. (Measured: 105 rows, 105 unique ids, 0 tiers outside `working | mid | prime | trophy`; distribution `mid` 44, `prime` 29, `working` 26, `trophy` 6.)

**The derived-tier check (AC-10A-12-TIER-DERIVE).** `classify.ts` must reproduce the shipped `role` column for all 105 districts **from the tier table and the flags alone**. The test proves it **derives** rather than copies by **removing the `role` column from the input** and re-running the derivation - if the derivation still reproduces the 105 roles, it is deriving; if it fails, it was copying. That is the difference the Producer's ruling asks for, and it is a **test**, not a paragraph.

**Why the tier cannot come from the flags alone (measured).** The role is **not** a function of the four flags: grouping all 105 districts by their flag tuple gives 8 groups, and **2 of them are ambiguous** - `(cbd=false, port=false, station=false, riverOrCanal=false)` covers four roles (`INDUSTRIAL`, `MIXED_CORE`, `PRIME_RES`, `TROPHY_RES`) and `(cbd=false, port=false, station=false, riverOrCanal=true)` covers three (`INDUSTRIAL`, `MIXED_RIVER`, `TROPHY_RES`). The tier is what separates them, so the tier input is **load-bearing**, not decorative. (Measured on the shipped flags file joined with 22 §3.3's table: 105 of 105 rows reproduce their shipped `role` under the derivation above, **0 mismatches**.)

### Count caps (the third table, beside `FACILITY_RULES` and `BUFFER_M`)
A per-mille share table **cannot express a count cap**. The card has two, and they are a **different constraint** from the Allowed-roles column: Allowed-roles is **membership** (may this sector be present in this role at all), a count cap is **cardinality** (how many). The mix needs both, so the caps get their own table and their own field and their own AC.

| Facility | Cap | Field | The prose it comes from |
|---|---|---|---|
| `fh_restaurant` | **1 per TROPHY_RES district** | `maxPer: { perDistrictRole: { TROPHY_RES: 1 } }` | "nothing in TROPHY_RES except one `fh_restaurant` per district" |
| `fin_exchange` | **1 per city** | `maxPer: { perCity: 1 }` | "at most 1 exchange per city" |

**The cap beats the mix band, and the card says so explicitly** (Producer ruling, 2026-10-22). `AC-10A-12-AUDIT-REF` accepts a **±150 per-mille** band around the mix target; measured, for a target of 20 per-mille the band is `[0, 170]`, so for any district with **N ≥ 12** non-RES parcels the band would **permit 2 restaurants** - which the cap forbids outright. **The band is a tolerance around the mix target; it never licenses exceeding a count cap.** Where the two conflict, **the cap wins**, and the capped cell is audited by **AC-10A-12-COUNT-CAP**, not by the histogram band. The AC's "≥ 5 parcels in the district" escape clause is **not** a waiver of the cap: a capped facility can occupy at most 1 parcel, so a capped sector is always skipped by that clause, and the cap is therefore the **only** check that ever applies to it. This is why the count-cap AC exists and why it is a separate AC.

**`AC-10A-12-COUNT-CAP`** (U5, with a committed mutant): for every facility with a `maxPer`, the realised count respects the cap - at most `perCity` in the city, at most `perDistrict` in a district, at most `perDistrictRole[role]` in a district of that role - over the reference region and across the 50 seeds of AC-10A-12-CLEAN. **A committed mutant is required**: a mutant in which `assign.ts` places a second `fh_restaurant` in a TROPHY_RES district, or a second `fin_exchange` in a city, must be **killed** by this AC (house pattern: T10A-13's committed 13-mutant baseline).

**Role mix (`DISTRICT_ROLE_MIX`, per-mille of non-RES assigned parcels, targets for the solver).** This is a **legibility target only** (Quant decision 1: placement has no economic link, so the mix is not calibrated to employment). Every row sums to 1000 (AC-10A-12-MIX-SUM), and a row is **0 for any sector that no facility of that sector may use in that role** - the "Allowed roles" column of the sector table above is the authority. That makes the table total, and replaces the three partial rows the pre-recut card left open (it carried only CBD, PORT and INDUSTRIAL, and each of those listed some sectors without saying whether the others were 0, so their sums were unverifiable).

**The unit, stated once (Producer ruling, 2026-10-22; Studio's finding).** The mix is a **relative priority between sectors, not a count**. The per-mille numbers say what a district should **look like** - the ratio is what the eye reads; the count is what the land does. The solver reads the mix deficit as a **count** and steers toward it; the **absolute** number of facilities in a role is decided by that district's **parcel count**, which T10A-03 produces and this card does not. Concretely, three things follow, and all three are part of the card:
1. **The denominator does not exist yet.** The mix is per-mille of non-RES assigned parcels, and `packages/citygen/src/` does not exist on `origin/main` and T10A-03 is unchecked in BUILD-ORDER, so the same cell buys wildly different numbers of facilities at different parcel counts. **"How many towers are on the Financial Mile" is therefore not determined by this table**, and the card must not pretend otherwise.
2. **The per-mille numbers are compared WITHIN A ROW ONLY** - never across rows. The moment a CBD cell is compared to a PORT cell, the 450 in PORT implies "this port has more of everything", and the two districts have different parcel counts, so that comparison is meaningless. **Within-row only.**
3. **The mix may never be read as a target absolute count.** A cell is a weight, not a quota.

**How "allowed in that role" is defined, so the biconditional is checkable.** The AC reads the **rules data**, not the prose table: a sector `S` is **allowed in role `R`** iff **at least one** `FacilityRule` in `FACILITY_RULES` with `sector === S` has `R` in its `allowedRoles`. The prose table above is the human-readable form of that same fact and the two must agree (AC-10A-12-MIX-SUM reads `FACILITY_RULES`, so a disagreement between the prose and the data fails the test). Per-facility narrowing is honoured, because "allowed" asks only whether **one** facility qualifies - so `FOOD_HOSPITALITY` is allowed in `TROPHY_RES` (the rules allow one `fh_restaurant` per trophy district), `HEALTH` is allowed in `TROPHY_RES` (a `hl_clinic` is not a hospital) but **not** in `PORT` or `INDUSTRIAL` (clinics are "any role but PORT, INDUSTRIAL"), and `ENERGY` is allowed in every role except `TROPHY_RES` (the substation). Measured on the shipped table: **104 cells, 0 forward violations, 0 reverse violations.** Re-verified independently against City Dev's in-flight `rules.ts` (branch `city/t10a-12`, 43 facilities, read per facility with `excludeRoles` applied): **104 cells, 0 forward violations, 0 reverse violations, 37 zero cells, 8 rows summing to 1000.** The biconditional holds against the **code**, not only against the card's prose.

**DECISION D-10A-12-MIX (Designer, 2026-10-22) - the per-mille values are a LEGIBILITY choice, not an economic one.** The per-mille numbers below are a **readability target**: they say what a city block should *look* like, so a district reads as a recognisable place (a financial mile, a dock, a workshop belt) rather than as a random scatter. They are **not** calibrated to employment, to output, to land value, to demand or to any other economic quantity, because the placement code **neither reads nor writes** V, rent, `amenityMult`, `location_j`, appraisal or demand, and its per-mille numbers are **not calibrated** to those quantities (INV-PLC-4; Quant's ruling of record, 2026-10-22). A reviewer who wants different per-mille numbers is making a **legibility** change, and changes one number on this complete table - not a change to the meaning of the table.
The values are **not** a Quant balance input and are not calibrated by Quant; the per-mille split inside a row is the Designer's call, on the single constraint that the row sums to 1000 and that a non-zero cell names a sector with at least one facility allowed in that role (AC-10A-12-MIX-SUM).

**The one sentence this decision does not make.** The earlier text justified the mix's non-calibration with "nothing this card emits enters V, rent, `amenityMult`, `location_j`, appraisal or demand". **Quant withdrew that claim on 2026-10-22**: it is false for two paths (Path A, the use-class chain, and Path B, the NPC-pool stock chain), and the card's boundary is now the narrowed claim in the Goal. **What this decision still asserts is only what is checkable**: the per-mille numbers are **not derived from** any economic quantity, and no economic module reads `DISTRICT_ROLE_MIX`. It does **not** assert that the city cannot respond to the shape of a district.

**The mix IS a steering lever, by design (Quant, 2026-10-22).** `assign.ts` picks the **argmax of score + mix deficit**, so the mix genuinely steers which sector takes a parcel. That is **legitimate and intended**: the mix only chooses **which sector takes a parcel that zoning already permitted**, so it cannot change V, rent, `amenityMult`, `location_j`, appraisal or demand, because no economic module reads placement output (the economics -> placement direction is what the card claims, and it holds). **Nothing in this card forbids the mix from steering.** What the card forbids is the mix being used as a **value** term, and what the new AC-10A-12-NO-ECON clause 2 forbids is the mix being used as a **lever on the indirect economic channel** (use class -> jobs -> `D_d`). A legibility solver that uses the mix to make a district read as a dock belt is doing exactly what the card is for.

## State model
1. **Static content:** `FACILITY_RULES`, `BUFFER_M` and `DISTRICT_ROLE_MIX`, versioned by `PLACEMENT_RULES_VERSION`. A change to the rules bumps the version. Regions already generated keep their assignments (10 §3.19.1: topology is persisted and never regenerated by replay).
2. **Derived, per region at generation:** `DistrictRole` per district and `LotType` per parcel (pure functions of persisted rows), then `Suitability[]` per (parcel, facility), then `PlacementAssignment[]`. Assignment runs as **stage 7b**, after T10A-03 stage 7 (land value and zoning) and before stage 8 (buildings), so stage 8 can read `styleKey` and `densityBand` as hooks.
3. **Persisted:** `PlacementAssignment` per non-RES, non-GREEN, non-reserved parcel. It is stored with the region (IR-2) and published as `sectorKey` and `styleKey` on the public binding (IR-3).
4. **Runtime (after genesis):** assignments are not re-rolled. When 09 calls `city.requestPremises` (10 §3.15), the eligibility filter (10 §3.15.2, 10 §3.21 "zoning permits the use") also drops units whose parcel has `EXCLUDED` suitability for the business's facility class (IR-4). A player's development plan (`prop.dev.plan`) for a facility class is rejected with reason `PLACEMENT_EXCLUDED` when the parcel's suitability is EXCLUDED (IR-4). Inside the rules, players choose freely. PREFERRED is only a tie-break for NPC fabric and the auto slot choice, never a value term.

## Implementation steps
1. **rules.ts:** the table above as data. Every `FacilityClass` is unique and prefixed by its sector's short code. Footprint min < max, and `lotTypes` is non-empty. `styleKey = 'style.sector.<sector lowercase>.<facility>'`.
2. **classify.ts:** `districtRole` from the T10A-13 district-flag data (tier + the `cbd` / `port` / `station` / `riverOrCanal` flags), with the order cbd -> port -> working -> trophy -> prime -> station (mid) -> riverOrCanal (mid) -> MIXED_CORE, and the result equal to the `role` column of `packages/content/data/district-flags.json` for all 105 districts. The **tier comes from `packages/content/data/district-tiers.json`** (22 §3.3's `Tier` column, transcribed by City Dev; see "Where the tier comes from") - **not** from `district-flags.json`, which has no tier column, and **not** from T10A-02, which is not built. The tier is **derived**, never copied: `classify.ts` must produce the 105 roles from the tier table and the flags **with the `role` column absent from its input** (AC-10A-12-TIER-DERIVE). `lotType` from zoning class, area, frontage, access and `reservedFor` (CIVIC and GREEN pass through; `reservedFor` parcels are never assignable).
3. **buffers.ts:** exact integer edge distance between polygons through T10A-03 predicates (no floats in the decision; squared distances compared in integers or bigint).
4. **suitability.ts:** for each parcel and facility, EXCLUDED if the role is in `excludeRoles` or missing from `allowedRoles`, the lot type is not allowed, the area is outside the footprint, a `needs` item fails, or a buffer to an existing receptor fails. Otherwise ALLOWED, or PREFERRED if the role is preferred. The score is an integer: 1000·preferred + 100·(near rules met) + floor(lotType rank bonus). Reason codes form a closed set (`ROLE`, `LOT`, `AREA`, `NEED_<x>`, `BUFFER`, `RESERVED`).
5. **assign.ts:** process districts in `districtId` order and parcels in `pcl_` sequence order. Facilities with hard anchors (exchange, port terminal, tank farm, plants, hospital, data center) are placed first. Within each step, pick argmax of score + mix deficit, with ties broken by **one** draw from the injected stream per tied set (sorted candidate list, index = floor(draw·n)). Each placed N2/N3 facility updates the receptor exclusion and each receptor updates the facility exclusion, so the output is buffer-clean by construction. There is no `Math.random`, `Date` or float in a discrete decision, and draws are quantised the way 10 §3.19.1 requires.
6. **Reference map (tests/e2e/city/fixtures/generate-city.ts):** keep the geography, streets, districts, landmarks and crown sites unchanged ("the existing map is great"). Replace the random `company_hq` and `storefront` picks with `assignSectors`. HQs go only where the HQ's facility rule allows, so finance HQs sit in Financial Mile and logistics HQs in Eastside Docks or Financial Mile. Awnings take the assigned sector. Industrial and port parcels gain warehouse, plant and terminal footprints from the rules' area ranges (Studio styles them; until then the fixture keeps today's 4 style slots, mapped from `densityBand`). The fixture's local xorshift stays tooling-only, but its draws are seeded per stream name (`city.gen:cty_port_avalon:<region>:sector`) so the fixture mirrors the engine's stream separation. The fixture's `SectorId` (market sector) for each binding is derived from the BizSector mapping table above.
7. **placement-audit.ts:** a pure audit over a built world that returns the violations (role, lot, area, buffer) and the per-district sector histogram. It is used by the e2e spec and by AC-10A-12-AUDIT-REF.

## Invariants
- **INV-PLC-1 (no exclusion):** no persisted assignment has EXCLUDED suitability under the rules version that made it.
- **INV-PLC-2 (buffers):** for every N2/N3 facility and every receptor, the edge distance ≥ `BUFFER_M`, in both directions, including receptors created after genesis.
- **INV-PLC-3 (determinism):** `assignSectors(region, draw)` is a pure function. The same region rows and the same stream give byte-identical canonical output, and draws come only from `city.gen:<cityId>:<regionId>:sector`.
- **INV-PLC-4 (economics isolation):** the placement code **neither reads nor writes** V, rent, `amenityMult`, `location_j`, appraisal or demand, and its per-mille numbers are **not calibrated** to those quantities. The **direct** half is a static import scan in both directions (AC-10A-12-ISOLATION); the **indirect** half (placement -> use class -> jobs -> `D_d`, and placement -> use class -> NPC pool stock -> `supply_{d,u}`) is bounded by AC-10A-12-NO-ECON clause 2 and its sub-clauses 2.2 and 2.3. The invariant is what the card can **enforce**; it is deliberately not the stronger "no output of this card enters those quantities", which Quant **withdrew on 2026-10-22** as false for two named paths.
- **INV-PLC-5 (closed sets):** every `sector` is one of the 13, every `sectorKey` is `SECTOR_<sector>`, and every `styleKey` resolves to a rules row.

## Exploit analysis
- **Value farming by placement:** placement adds no value term (INV-PLC-4, clause 1). A player gains nothing by steering a sector onto a lot except the existing, priced location economics of 10 §3.15.3 and §3.6.3, which already cost rent through `amenityMult`. **The indirect channel is the honest edge of this claim**, and it is now **two** channels, both named and bounded. Path A (use class -> jobs -> `D_d` -> rent / `location_j`) is a **genesis** property, fixed before anyone plays, bounded by clause 2 and measured as small and self-limiting (a 1% job-attribute shift at the mean moves 90-day rent by **9 basis points** and market share by **0.15%**). Path B (use class -> NPC pool `<use>` -> `supply_{d,u}` -> rent) is **closed by construction** by clause 2.3, because the pool's `<use>` comes from **zoning** and placement never sets a pool's stock. **There is no player-facing lever on either path**, and clause 2's mutants are the evidence that the mix can never be used to push a district's desirability around after the fact.
- **Adjacency stacking (clustering a sector to farm a cluster bonus):** this card defines no bonus. The existing café cluster bonus (09 twist) is untouched and remains 09's to cap. The `near` pulls are placement tie-breaks only.
- **Griefing housing (buying a lot next to homes to put in heavy industry):** N2/N3 classes are EXCLUDED within the buffer and outside INDUSTRIAL/PORT roles, so `prop.dev.plan` fails with `PLACEMENT_EXCLUDED` before any money is spent. Rezoning (10 §3.11.3) can change the use but not the buffer or role exclusion.
- **Reverse griefing (building housing next to a plant to force it out or to claim nuisance):** the buffers are symmetric. A RES project inside an existing N2/N3 buffer is EXCLUDED, and an existing facility is never evicted or devalued by later receptors.
- **Denial by lot hoarding (buying every port yard to block rivals):** the scarcity is real and already priced. Port yards are listed through 10B land auctions, and NPC fabric holds most yards. The auto slot choice (10 §3.15.2) falls back to pending placement and never blocks the purchase. No new mechanic is added.
- **Seed or stream gaming (re-rolling a region for a better layout):** generation happens once and is persisted. The stream is root S and never exposed to players, and a rules-version bump never regenerates existing regions.
- **Exclusion bypass by mislabelled facility (calling a refinery a warehouse):** the facility class comes from the business type (09 catalog to facility map, IR-5), not from player input.

**The preferred facility per (role, sector) cell - the card states how the solver picks (Producer ruling, 2026-10-22).** The rules table carries one "Preferred roles" column per **sector**, but the data model is per **facility** (`FacilityRule.preferredRoles`), and a mix cell names a **sector**. - **AC-10A-12-NO-ECON** has **three clauses**, and all three must pass. It is a **test the card can actually fail**, not a paragraph (Studio and Quant agree on this point).
  - **Clause 1 - the direct boundary (import scan).** No engine price, rent, demand, valuation or **employment** module imports placement output (`placement/**`: buffers, assign, audit, rules, classify). Any future economic use needs a new Quant ruling first.
  - **Clause 2 - the indirect channel (a check, not a paragraph).** Placement can reach the economy **without an import**, so clause 1 alone cannot carry the claim. The check must show:
    1. **placement output does not determine which use class sits in which district beyond what the district's own `DistrictRole` and the sector rules already imply** - a use class reaches a district only because that district's role and that sector's rules admit it, never because a per-mille number put it there; and
    2. **the mix is a target for a legibility solver, not an input to any demand or employment computation** - **no demand, jobs, `jobsAccess_d`, `D_d`, rent, `location_j` or valuation module reads `DISTRICT_ROLE_MIX`**, and no demand, jobs, `jobsAccess_d`, `D_d`, rent or `location_j` computation takes a mix term.
    **The formulation is the builder's choice, but the property is not.** The card does not prescribe how to check it (the solver does not exist yet). What it requires is that **a test exists that would FAIL if the mix were ever used as a lever on that channel**, and that the test carries at least one committed **mutant** in which the mix is used as such a lever - for example a mutant in which `assign.ts` lets a mix deficit override the use class that the district's role and the sector rules admit, or a mutant in which a demand or employment module reads `DISTRICT_ROLE_MIX`. Only the facilities that list a kind may carry it (for example `log_port_terminal`: STS_CRANE, RTG_GANTRY; `ma_bulk_terminal`: SHIP_LOADER; `en_plant`: STACK, COOLING_TOWER; `en_tank_farm`: TANK, FLARE; `mf_heavy`: CHIMNEY; `ma_grain_silo`: SILO; `me_broadcaster`: MAST). Plant halls and sheds are buildings and clamp to `maxHeightM`. **AC-10A-12-STRUCTURES:** every structure kind on a rule has a cap; no emitted structure exceeds its cap or appears on a facility that does not list it; no structure adds area, FAR, `heightLevel` or a crown title; and a building part above `maxHeightM` fails.
2. **Chip fab.** The new lot type `FAB` is distinct from PLANT and CAMPUS: a clean-room site that requires GRID_MW. `mf_chip_fab` uses FAB only. FAB lots are derived only in INDUSTRIAL roles with grid capacity. **AC-10A-12-FAB:** `mf_chip_fab` is placed only on FAB lots, FAB lots occur only in INDUSTRIAL roles with GRID_MW, and no other facility uses FAB.
3. **Quay edge and rail access.** `parcelFlags` derives three flags from persisted terrain and the street and rail skeleton. `quayEdge` is the cm polyline of each parcel edge within 200 cm of water that carries a quay wall, or null. `railAccess` is true when a rail line or siding lies within 30 m of the parcel edge, and `railPointCm` gives the nearest point. 4. **Buffer land (amended).** Buffer land is **not** turned wholesale into GREEN. Real cities fill the gap between heavy plants and housing with non-housing uses, and forcing all of it green would remove usable INDUSTRIAL supply that 10 §3.19.4 zoning provides. Inside an N2 or N3 buffer, a parcel may take any non-receptor facility whose nuisance class is no higher than the source's. Only parcels for which no such facility is suitable become `bufferGreen` GREEN. Every parcel inside a buffer, green or not, is EXCLUDED for receptors (RES, hospital, school) and for RES development or rezoning, and bufferGreen parcels can't be sold for housing. Buffers are set at generation. A later facility never converts existing parcels, and owned assets are never changed by a visual rule (10 §3.11.12, LC08). Studio styles bufferGreen parcels as tree belts. **AC-10A-12-BUFFER-GREEN:** every parcel inside a buffer is either a non-receptor facility or bufferGreen; no receptor or RES zoning sits inside a buffer; no bufferGreen parcel accepts a RES plan or a housing listing; and generation leaves existing owned parcels unchanged.
5. **Visual seed.** Each parcel has a stable visual key `city.vis:<cityId>:<parcelId>`, built only by `cityVisKey` (E-68 helper rule; registry row via IR-7). The seed is a hash of that key, so the client can reproduce it without any server state. It never draws from `city.gen:…:sector` or any other stream, so look changes can't alter placement and placement changes can't shift looks. **AC-10A-12-VIS-SEED:** visKey is the same for the same parcel across runs and rules versions; changing the sector stream or the rules leaves every visKey unchanged; and a scan finds no literal `city.vis:` string outside `cityVisKey`.
6. **Crown parcels.** `crownParcel` is true exactly where `Parcel.reservedFor === 'CROWN'`. Per 10 §3.22, `PARAM.crown_parcels_per_city = 6` for each slot-1 capital and CBD, with a height cap of 1.5× the district cap. Crown parcels are never sector-assigned at genesis. Their band is TOWER, and the brass treatment applies only once a tower is completed there. **AC-10A-12-CROWN-FLAG:** the flag is set on exactly the CROWN-reserved parcels; engine output has 6 per eligible city (the reference fixture keeps its 2 until U6 adds 4, see AC-10A-12-CROWN-SIX); and no crown parcel carries a sector assignment.
7. **Mining and agriculture off the map.** There are no fields, quarries or mines in the city envelope, because 09 SITE businesses live off-map. The only in-city facilities are the three in-city facilities (`ma_trading_office`, `ma_bulk_terminal`, `ma_grain_silo`) plus rail spurs. The terminal, silo and spurs are allowed only in PORT and INDUSTRIAL roles. Studio's fringe treatment (allotments, field boundaries) is GREEN, not MINING_AGRICULTURE. **AC-10A-12-OFFMAP:** MINING_AGRICULTURE has exactly those three facilities; silos, terminals and spurs appear only in PORT or INDUSTRIAL roles; and no parcel is assigned a field, quarry or mine.

# SPEC EXCERPTS (verbatim; binding game rules)

**[10 §1 Purpose]** (context)

## §1 Purpose

1. **A quieter wealth-building path with real economics** (old E01–E08). Property gives recurring income, leverage, appreciation and development profit, and needs far less attention than trading, companies or AI. A player can make property their main playstyle and win.
2. **Everything is physical and addressed.** Every property is a real building (or a unit inside one) on a real parcel with a permanent address in a procedural city that is the same on every device. Every business occupies real premises. Every listed company has a headquarters. The city is the economy drawn as a place (old 06 §1, LC01–LC05).
3. **Cities are economies.** Each city has a population, households, jobs, rents, vacancies and a construction pipeline. Rents and values come from demand against supply by district and use. A rate hike, an employer arriving, a district being redeveloped or a credit crunch all move property for explainable reasons on the same tick they happen (V3 §2.4).
4. **Growth is caused.** A city grows when sustained demand exceeds usable supply and someone (NPC developer or player) builds. It declines when demand leaves. The visible city is a projection of this one simulation; it never grows from a decorative score (LC07 adopted, old 06 §7 superseded).
5. **Leverage is how fortunes are made and lost.** Mortgages with LTV covenants, refinancing risk and forced sales tie property to 04 rates and 07 credit; a housing crisis can emerge from rules.
6. **Status with a privacy contract.** Addresses, storefronts, headquarters, homes, recognition and cosmetic flex exist, but the public city is built from an allowlist of public facts and never reveals positions, P&L or presence (L11, LC16).

### §3.15 Company premises and business location (E07, I02, I06)

1. **Every business occupies premises.** When 09 creates or relocates a business, it requests a unit through `city.requestPremises(bizId, cityId, districtId?, use, minArea, slotPreference?)`. 10 returns a unit (a storefront slot for RETAIL/consumer businesses, an office floor, a warehouse, a hotel, a data-center site) and creates a lease from the unit's owner (NPC pool by default) at the unit's market rent. The business pays that rent as an operating cost (09).
2. **Slot choice.** If the player picks a slot on the map, they get it if free; if they pass a district only, 10 chooses `argmax` over free eligible units of `slotScore − 0.0001·hash(bizId, unitId)` where `slotScore` = frontage bonus (§3.6.3) + 0.5·D_d. If no unit is free, 10 reserves the business in a **pending placement** state (LC17): the business operates from a temporary unit at 90% capacity and the pending state is shown; it gets the next unit that frees or completes in that district, in queue order, never by blocking the purchase on generation.
3. **Location is explicit economics** (LC09 resolved). 09's attractiveness term `location_j` is supplied by 10: `location_j = 0.25·frontageBonus_unit + 0.50·D_d + 0.25·tanh(ln(hhDemand_d / meanHhDemand_city))`. A better location therefore helps the business and costs more rent through `amenityMult`; cosmetic purchases (§3.25) never change `location_j`, rent or demand.
4. **Owner-occupied premises.** If the business's owner chain also owns the unit, the lease is **related-party**: rent is an intercompany transfer that 03 eliminates on consolidation (no group profit), but the unit still shows its foregone market rent as an opportunity cost on the business and prop cards (I02). A related-party lease must be at market rent ±10%; outside that band 03 treats the difference as a distribution and 13 may review it for minority-shareholder harm when the business or prop sits in a company with outside shareholders (I07).
5. **Labs and data centers** request DATACENTER_SITE premises (11 §3.3.4) with a power requirement in MW; the site's grid capacity binds.
6. **Headquarters** for player companies: a company may designate an owned or leased OFFICE prop as its HQ; it appears as a COMPANY_BUILDING binding with the company's name (public, because a company and its HQ are public, LC05). A listed player company that reaches the top 25 market caps of its home city gets an HQ slot offer in the CBD (§3.20.1).

### §3.19 The procedural city (generation)

The generator turns a city's **personality** and seed into persistent geography, roads, blocks, parcels, buildings and landmarks. It runs on the server in a worker, never in the tick; its output is persisted and is the authoritative physical city. The economic stock (§3.0) is initialised from it.

#### §3.19.1 Determinism and packaging

- Pure TypeScript package `@game/citygen` with no DOM, no `Math.random`, no wall-clock reads (old 06 §4). RNG: 02's xoshiro128** with one stream per `(cityId, regionId, stage, featureId)`.
- All topology decisions use **fixed-point integer centimetres** and robust integer predicates (orientation, segment intersection); floats are allowed only for continuous fields (noise, land value) and are quantised before any discrete decision. The noise implementation is the package's own (no third-party library).
- The generator package version, its dependency lockfile and the Node runtime are pinned per region (LC14). Generated topology is **persisted** (19 tables) at the moment a region is generated; it is never regenerated by replay. Client code never runs topology steps (old 06 §8.2).

#### §3.19.2 Envelope, regions and chunks (LC14)

- Each city has a bounded **envelope** (`PARAM.city_envelope_km`: 6 km × 6 km standard, 9 × 9 for slot-1 capitals) with a **macro plan** generated at genesis for the whole envelope: terrain (2 m height grid at 16 m sampled macro resolution), water bodies, coastline, rivers planned at basin scale (not per chunk), protected land, the arterial skeleton, landmark axes, district plan, and **reserved development corridors**.
- The envelope is divided into **generation regions** of 512 m–2,048 m (sized by morphology: dense wards 512 m, suburbs 2,048 m). Each region has boundary contracts (crossing coordinates, street class, width, elevation, water edges). Adjacent regions consume those contracts, so seams match.
- Regions are generated (detail streets, blocks, parcels, buildings) at genesis for the developed core plus one ring, and later on demand when growth reaches a reserved corridor (§3.21.5). Generation of a region is idempotent and transactional: persist all features, then publish.
- **Render/transport chunks** of 128 m × 128 m are cut from generated regions after generation, for streaming only. A block, parcel or building crossing a chunk boundary has one owner chunk and references from others.

#### §3.19.3 Pipeline

| Stage | Output | Method |
|---|---|---|
| 1 Terrain and water | height, water mask, slope | domain-warped fBm (4–6 octaves, one warp); coastline as a personality signed-distance shape perturbed at two scales; rivers by basin-scale flow accumulation on the macro grid with smoothing; canals as authored polylines refined along the street field |
| 2 Skeleton | arterials, crossings, landmark axes, transit lines | authored constraints per personality (port basin, bridges, diagonal boulevard, rail loop, coastal spine) placed first, then arterials traced from the old centre, port and bridges along the tensor field with long separation |
| 3 Historic core | connected short-segment growth around old centres, quays and squares | agent-based growth: segments extend 20–60 m with ±25° wander, branch probability 0.3, snapping to nodes within 6 m, stop at water and steep slope; max unserved block 8,000 m² |
| 4 Planned extensions | collectors, local streets | tensor-field hyperstreamlines (grid, radial, boundary, heightmap basis fields per personality); separation: collectors 120–200 m, locals 40–90 m; orientation quantisation per district (strict 0°/90°, soft ±8°, free) |
| 5 Graph constraints | cleaned planar graph | intersection angle ≥ 35°, no edges < 8 m, no near-parallel duplicates within 10 m, connected arterial routes, every block reachable by ROAD or FOOT (pedestrian access is valid where the personality marks it, e.g. Meridia islands) |
| 6 Blocks and parcels | blocks, parcels | blocks = faces minus road widths; blocks under 300 m² become plazas, very irregular remainders parks; parcels by frontage-preserving oriented-bounding-box splits to the district's target frontage and depth (log-normal jitter); deep or irregular blocks use a courtyard fallback (perimeter strip parcels, interior court as green or shared yard) |
| 7 Land value and zoning | V field, zoning per parcel | §3.19.4 |
| 8 Buildings | archetype and parameters per parcel | shape grammar §3.19.5, heights from V and district caps |
| 9 Landmarks | one landmark per district | best parcel by V with frontage on a square or water; partly authored template plus procedural details |
| 10 Life | trees, traffic lanes, boat lanes, rail | cosmetic, seeded, client-side drawable data only |

#### §3.19.4 Land value field and zoning

```
V(p) = Σ_centres A_c · exp(−d(p,c)² / (2σ_c²)) + w_water · view(p) + w_hill · elevation(p) · prestige(district)
     + w_transit · exp(−d(p, station)/λ) + districtOffset(district) + ε · noise(p)
```

Coefficients `A_c, σ_c, w_*, λ, ε` per personality. District borders follow streets (a block belongs to one district), from the personality's district plan (seed point, preferred terrain role, target area). Zoning is a function of V, district tier and terrain: residential ladder (houses → row houses → mid-rise → high-rise), commercial (shops → offices → towers; ground floors of commercial parcels become storefront slots), industrial (warehouses, plants, port, data-center-eligible parcels where the grid allows), civic (stations, museum, city hall, stadium; never sellable), green. Slopes above the personality threshold become parks or stairs. `maxHeightM = min(districtCap, V-derived cap)`, `maxFar` per zoning class (house 0.6, row 1.2, mid-rise 3, high-rise 8, office tower 15, CBD 25).

#### §3.19.5 Building grammar

```
Lot   → Podium(h_p) Shaft(h_s) Crown        (towers)
      | Body(h) Roof                        (houses, row houses, mid-rise)
      | Shed(h) SawRoof                     (warehouses, plants)
Shaft → inset 10–30%, optional setbacks every k floors, optional twist (Kaiyo)
Crown → flat | spire | lantern | stepped | dome | helipad | antenna cluster | garden
Roof  → gable | hip | mansard | flat with props | sawtooth
```

Each district has 6–10 archetypes with parameter ranges (floor height, bay width, window style, material, setback rhythm, roof props). Heights: log-normal with median from V and district index at generation, clipped by caps, spatially correlated by a low-frequency height noise, with occasional outliers. Each building carries a seed; neighbours never share an identical parameter set except within an authored repeating terrace (tagged, LC18). `BuildingVisual` stores: parts (1–4) with base mesh id, size, quantised rotation, style id, seed, floor height, bay width, tint index. Economic mapping: archetype → `propertyType` and unit plan (e.g. mid-rise 6 floors × 4 units of 75 m² = APARTMENT_BLOCK variant with 24 units).

#### §3.19.7 Genesis calibration (city size ↔ economy)

At genesis the generator develops parcels in priority order (§3.21.3) until the developed stock matches the launch economy: residential units = `households · (1 + naturalVacancy_RES)`, office area = launch office jobs × 14 m² × 1.08, retail = population × 1.4 m² × 1.06, industrial = industrial jobs × 55 × 1.07, hospitality = population × 0.35 × 1.10. Buildings get synthetic ages (log-normal median 35 GY, older in heritage districts) and conditions `clamp(N(80, 10), 40, 100)`. This guarantees the visible city and the economic stock are the same thing (pillar "everything is real", old 06 §2). Port Avalon at launch: about 104,000 households, about 15,000 residential buildings, 1,900 commercial buildings, 600 industrial; about 18,000 buildings total.

#### §3.11.3 Zoning and permits

1. **By right**: the project's use is in `zoning.allowed`, height ≤ `maxHeightM`, FAR ≤ `maxFar`. Permit review takes `PARAM.permit_days_by_right (2)` GD for ≤ 5,000 m² and 5 GD above; fee 0.4% of hard cost (`RE_PERMIT_FEE`, SINK); approval probability 0.98 (rejection only for ACCESS, a deterministic check shown before submission).
2. **Variance** (height up to +30% or FAR up to +25%): 7 GD, fee 1%, `pApprove = clamp(0.35 + 0.20·[pressure_{d,use} > 1.10] + 0.10·[grade A] − 0.25·heritage − 0.10·objections, 0.05, 0.85)`.
3. **Rezoning** (a use not allowed): 14 GD, fee 2%, `pApprove = clamp(0.20 + 0.25·[pressure of new use > 1.10] − 0.30·heritage + lobbyBonus (16, ≤ 0.15), 0.02, 0.70)`.
4. **Objections**: any player owning a property within 150 m may file an objection (fee $5,000, `PROP_OBJECTION_FEE`, TRANSFER to the city government; class and amount [Quant] confirm, E-39; max one per project per objector); each objection lowers pApprove by 0.05 up to −0.20. Objection by a competitor with no nearby property is impossible.
5. **Rejected**: fee is lost; the developer may appeal to 13's planning tribunal with `prop.dev.appeal` (cost $25k + 0.2%, `PROP_PLANNING_APPEAL_FEE`, SINK like 13's `LAW_COURT_FEE`; class and amount [Quant] confirm, E-39; 7 GD, success p = 0.30 if the rejection was by variance math, 0.0 for heritage locks).
Permit review capacity: each city's planning office processes at most `PARAM.planning_capacity_per_GD = 20 + 0.0001 · population` reviews per GD; extra applications queue FIFO. Players see their queue position.
